# Как отслеживать отказы на сайте кроме Яндекс.Метрики

Яндекс.Метрика и Google Analytics отвечают на вопрос **«сколько»**: сколько
отказов, какой процент, с каких страниц уходят. Но они почти не отвечают на
вопрос **«почему»**. Вы видите, что с карточки товара уходит 70% посетителей — а
что именно они делали за секунду до ухода, куда нажимали, что вводили, не сломалось
ли что-то у них в браузере — из отчёта об отказах не узнать.

Ещё нюанс: в Метрике «отказ» — это специфический термин (визит короче 15 секунд с
одним просмотром). Он не равен «человек ушёл, потому что ему что-то помешало».
А именно это и хочется ловить.

Разберём, как отслеживать реальные уходы с сайта и их причины — в дополнение к
Метрике, а не вместо неё.

## Чего не хватает в отчётах Метрики

- **Нет последних действий.** Видно страницу выхода, но не последовательность
  «кликнул → ввёл → перешёл → ушёл». А именно она объясняет уход.
- **Не видно технических причин.** JS-ошибка, упавший запрос, медленно
  загрузившаяся страница — всё это гонит людей прочь, но в отчёте об отказах не
  отражается.
- **Агрегаты вместо сессий.** Метрика мыслит процентами и сегментами. Чтобы
  понять конкретный уход, нужна запись конкретной сессии.

Вебвизор частично закрывает это, но он тяжёлый, пишет далеко не все сессии и в
нём неудобно искать именно точку отказа.

## Идея: связать «уход» с последними действиями

Технически уход с сайта — это событие `pagehide` в браузере. Лёгкий SDK ловит его
и пушит событие «конец сессии» (`SESSION_END`). Параллельно он всю сессию пишет
«хлебные крошки» (breadcrumbs) — осмысленные действия пользователя:

```ts
// Типы событий, которые считаем действием пользователя.
export const ACTION_TYPES = ["CLICK", "INPUT", "NAVIGATION"] as const;

// Сколько последних действий фиксируем перед отказом.
export const MAX_BREADCRUMBS = 3;

export function isDeparture(type: string): boolean {
  return type === "SESSION_END";     // уход с сайта
}
```

Теперь, имея поток событий, для каждого ухода можно восстановить: **на какой
странице ушёл** и **какие 3 последних действия** этому предшествовали. Последнее
действие — самое информативное.

Чтобы одинаковые по смыслу действия схлопывались в одну группу, метки
нормализуются — из ввода выкидывается само значение, из перехода — query-строка:

```ts
export function normalizeActionLabel(e) {
  if (e.type === "INPUT") {
    // «Ввод: email = вася@…» → «Ввод: email» (значение не храним)
    const msg = e.message ?? "Ввод";
    const cut = msg.indexOf(" = ");
    return cut >= 0 ? msg.slice(0, cut) : msg;
  }
  if (e.type === "NAVIGATION") {
    // «Переход: /cart?utm=…» → «Переход: /cart»
    const path = pathOf(e.url);
    return "Переход: " + (path ?? "—");
  }
  return e.message ?? e.type; // CLICK — как есть: <тег>#id «подпись»
}
```

## Что это даёт в аналитике

Собрав уходы за день, агрегируем два топа: **страницы ухода** и **последнее
действие перед уходом**. Именно связка «страница + последнее действие» показывает
паттерн, который в Метрике не виден:

- Уходят с `/checkout` сразу после «Ввод: card_number» → проблема на шаге оплаты.
- Уходят с `/product/*` после «Клик: кнопка Купить» → кнопка не срабатывает или
  ведёт в никуда.
- Уходят с `/search` после «Переход: /search» без единого клика → выдача пустая
  или нерелевантная.

Это гипотезы, которые можно проверять и чинить, — а не просто «процент отказов
вырос».

## Технические причины ухода — отдельный класс

Половина «отказов» — не про UX, а про то, что у пользователя **что-то сломалось**.
Поэтому кроме действий стоит писать:

- **JS-ошибки** (`EXCEPTION`) — необработанное исключение в его браузере;
- **упавшие сетевые запросы** — API вернул 500, форма не отправилась;
- **медленную загрузку** — событие `PAGE_LOAD` с длительностью выше порога.

Порог «медленного» задаётся в настройках и читается SDK — всё, что грузится дольше,
помечается как медленное:

```ts
// SDK читает slowMs из /api/logger/config и считает медленными
// запросы/страницы дольше этого порога (по умолчанию — из настроек проекта).
const PRESETS = [500, 1000, 2000, 3000]; // мс
```

Когда рядом с уходом в сессии висит `EXCEPTION` или медленный `PAGE_LOAD` — причина
ясна без гаданий. Это то, чего в отчёте об отказах Метрики просто нет.

## Как это выглядит в связке

1. Ставите лёгкий SDK на сайт (один тег, проект определяется по `Origin`).
2. SDK пишет сессии: действия, ошибки, время загрузки, уход.
3. На вкладке аналитики — топ страниц ухода и топ последних действий за день.
4. Разворачиваете конкретный уход → видите цепочку крошек и рядом — была ли ошибка
   или тормоза.
5. Чините причину, а не симптом.

Метрика при этом остаётся — она отвечает на «сколько и откуда трафик». А эта связка
отвечает на «почему конкретно уходят».

## Коротко

Чтобы отслеживать отказы глубже, чем это делает Яндекс.Метрика, нужны три вещи,
которых в ней нет: **последовательность действий перед уходом**, **технические
причины** (JS-ошибки, упавшие запросы, медленные страницы) и **привязка к
конкретной сессии**. Тогда «процент отказов» превращается в понятный список причин,
которые можно устранить.
